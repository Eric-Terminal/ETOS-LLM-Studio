# 本地 Linux 重置与快照恢复回归说明

## 已确认的代码问题

- `deleteSystem` 删除文件后立即调用 `ensureReady`，把下一次启动失败表现为重置失败。现在停止并清除系统后返回待安装状态，首次使用时再安装内置系统。
- 原生内核启动失败会保留非空闲状态，Swift 的 `runtimeStarted` 却可能仍为 `false`。重试前现在会检查原生状态并清理残留，避免直接重复启动。
- 启动、重置与重新启动会跨 actor 挂起。现在在首次挂起前登记任务，维护期间的新启动请求等待维护结束，页面刷新不能覆盖进行中的状态。
- 快照中的外部挂载书签若直接解析抛错，原代码没有撤销数据库里的 `available`。现在标记为需要重新授权，并在终端申请租约时查询当前内核的实际挂载；恢复的外部记录也不能占用内部挂载路径。
- 任务结束时原本在排空 bridge 诊断后才释放租约，而原生停止又等待这些租约。现在进程退出后先释放租约，再完成诊断；维护取消任务时也先等待退出并释放租约。
- “导入数据”曾把 `.elsbackup` 转为 `SyncPackage`，遗漏 Linux 环境变量、命令规则、提示配置与挂载等关系表。“从快照恢复”直接替换数据库，因此两个入口结果不同。现在双端导入入口都将快照交给完整恢复确认页，确认后调用同一个 `SnapshotRestoreService`，不再转换为同步包。

截图中的 `-114`、`-2`、`-16` 分别对应原生层的重复启动、挂载不存在和资源占用错误。上述问题由代码确认；缺少用户设备日志，不能认定已经复现其最早一次启动失败的完整过程。

## 验证范围

已补充 `LocalLinuxRecoveryTests`、`ThirdPartyImportETOSTests` 与 `PersistenceMigrationBackupTests` 回归用例，覆盖：恢复启用设置但系统缺失时重置成功、损坏系统的重复重置与用户文件保留、失效书签状态更新、保留路径冲突、普通与加密快照以及目录选取统一进入恢复确认、下载源删除后仍能使用待恢复副本，以及两个入口恢复同一快照后 Linux 环境变量保持一致。

本次按项目约定未运行构建或测试。已进行差异检查、本地化文件语法与文案覆盖检查，以及调用路径静态复查。

后续取得测试授权后运行 ETOSCore 测试；设备回归需在 iOS/watchOS 验证：从干净安装恢复旧快照、重置后首次打开终端、带失效外部挂载的恢复、终端和本地 MCP 活跃时重置，以及重置期间的并发启动。还需核对两个入口恢复 Linux 配置的内容一致，且取消恢复确认不会替换数据库。
